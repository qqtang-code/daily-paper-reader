## 摘要
Top-k稀疏注意力使长上下文LLM解码的计算成本降低：每一步仅读取几千个选定的KV条目，而非整个上下文。然而，服务系统通常将整个KV缓存保留在GPU HBM中，以便每个位置始终可被选择，因此请求的内存开销仍随其完整上下文长度增长——解码在计算耗尽之前很久就遇到容量墙，且KV缓存超过HBM的上下文根本无法被服务。我们提出HiSparse，一种用于稀疏注意力服务的精确、与索引器无关的分层KV缓存。HiSparse将每个请求的完整KV历史保存在主机内存中，并通过一个小的固定大小GPU缓存限制其解码内存占用；一个融合的CUDA内核在解码CUDA图内解析每一层的选择——命中检测、LRU替换和主机到设备获取；对于跨层共享选择的模型，精确的逐层预取隐藏了剩余未命中开销的大约一半。由于仅KV放置发生变化，模型输出保持不变。HiSparse已合并到上游SGLang中，并在H200、B200和GH200平台上跨三个稀疏注意力家族（DSA、NSA和Quest）进行评估：在长上下文工作负载上，峰值生成吞吐量提升高达4.7倍，同时保持可比的每token延迟并减少高负载下的首token时间——一个无IO的预言机显示解析机制本身不增加可测量的每token成本，使得主机-设备IO成为有界驻留的唯一代价。

## Abstract
Top-k sparse attention makes long-context LLM decoding cheap to compute: each step reads only a few thousand selected KV entries rather than the full context. Serving systems, however, typically keep the entire KV cache in GPU HBM so that every position stays selectable, so a request's memory bill still grows with its full context length--decoding hits a capacity wall long before it runs out of compute, and a context whose KV cache exceeds HBM cannot be served at all. We present HiSparse, an exact, indexer-agnostic hierarchical KV cache for sparse-attention serving. HiSparse keeps each request's full KV history in host memory and bounds its decode footprint with a small, fixed-size GPU cache; a fused CUDA kernel resolves each layer's selections--hit detection, LRU replacement, and host-to-device fetches--inside the decode CUDA graph; and, for models that share selections across layers, exact layer-wise prefetching hides roughly half of the remaining miss overhead. Because only KV placement changes, model outputs are unchanged. HiSparse is merged into upstream SGLang and evaluated across three sparse-attention families (DSA, NSA, and Quest) on H200, B200, and GH200 platforms: it improves peak generation throughput by up to 4.7x on long-context workloads while preserving comparable per-token latency and reducing time-to-first-token at high load--and a no-IO oracle shows the resolution mechanism itself adds no measurable per-token cost, leaving host-device IO as the only price of bounded residency.

## 一、核心问题与整体含义（研究动机与背景）

- **背景**：长上下文LLM（如DeepSeek-V3.2、GLM-5等）已成为编码代理、长文档分析等场景的标准工作负载。Top-k稀疏注意力（Sparse Attention）通过每步仅读取查询依赖的少量KV条目（通常数千个），使长上下文解码的计算代价大幅降低。代表性方法包括训练型的选择器（如DSA、NSA）以及训练无关的Quest。
- **核心矛盾**：尽管稀疏注意力将**读取**的KV数量从全上下文降低到k个，但现有服务系统仍将**完整KV缓存**驻留在GPU HBM中，以保证任何位置都可被未来选择。因此请求的内存开销仍随完整上下文长度增长——解码在计算资源耗尽前就先遭遇**内存容量墙**；KV缓存超过HBM的上下文甚至无法被服务。
- **量化示例**：以GLM-5.1（128K上下文）为例，单请求KV状态高达13.09 GB（BF16），1M token请求需要超过100 GB KV，直接占满整张H200的141 GB HBM。在32K上下文下，约60个并发请求即耗尽HBM；128K下仅能容纳约15个请求。
- **关键洞察**：稀疏选择器本身就是一个"免费预言机"——它在每层每步精确宣告将读取哪些位置；且选择具有强时间局部性（相邻步骤选集高度重叠）和跨层相关性（部分模型显式共享索引器输出）。这与缓存体系（小快速缓存 + 大慢速存储）的适用条件高度吻合。
- **论文主张**：HBM应为注意力**实际读取**的KV付费，而非为"可能读取"的全部KV付费。HiSparse因此提出一种精确、索引器无关的分层KV缓存方案，将GPU内存容量瓶颈转化为可调的主机-设备IO开销问题。

## 二、方法论：核心思想与技术细节

### 2.1 核心思想：解耦逻辑可用性与物理驻留

- 每个请求的**完整KV历史**保存在主机内存（pinned DRAM）中，保证所有逻辑位置始终可选；
- GPU侧仅保留**固定大小的缓存**（每请求每层B个KV槽位），解码内存占用由B决定，与上下文长度Lctx无关；
- 仅改变KV的物理放置位置，**不改变选择集、注意力分数或输出**，因此模型输出与基线完全一致。

### 2.2 系统架构与请求生命周期

请求经历四个阶段：

1. **预填充与暂存**：prefill阶段生成的各层KV写入主机KV池；索引器状态（如DSA的lightning indexer key）始终驻留GPU。
2. **准入**：请求的GPU缓存和元数据就绪后即可调度。每请求KV占用为 Nℓ·B·WKV·s（约0.4 GB@128K/GLM-5.1），而非 Nℓ·Lctx·WKV·s（13.09 GB），约30倍削减。
3. **逐层解码**：索引器产生选择集 → 融合resolve内核做命中检测/缺失获取/元数据更新 → 生成物理槽位向量 → 注意力内核执行。
4. **写穿透**：新生成token的KV直接写入GPU缓存预留槽位，并由专用流异步写回主机池。

### 2.3 三个关键技术机制

**（1）LRU缓存管理（保留局部性）**

- 缓存不仅是top-k暂存区，还保留B−k个最近使用槽位以捕获跨步局部性；
- 采用LRU替换策略，并做一处刻意优化：命中条目在最近使用顺序上排在本次新获取的缺失条目之前，使被反复选中的位置比一次性选择更抗驱逐；
- 各层缓存独立管理，不跨层协调驻留，跨层结构通过预取利用。

**（2）融合miss解析内核（RESOLVE）**

将命中检测、受害者选择、LRU更新、主机获取、元数据发布融合为单一CUDA内核，每层启动一次，并捕获在SGLang的稳态解码CUDA图中。其五个阶段为：

1. **构建top-k哈希表**：将选中位置装载入共享内存哈希表；
2. **探测GPU缓存槽位**：对每个B槽位做成员测试，标记hit/evictable；
3. **并行扫描与LRU更新**：压缩可驱逐槽位、选受害者、生成更新后的LRU元数据；
4. **批量获取缺失KV**：采用Strata的GPU-assisted IO技术，CUDA线程直接以向量化非相干load（ld.global.nc.v2.b64）从pinned主机内存获取，容忍分散地址并接近链路带宽；
5. **发布注意力输入**：更新页表，输出与选择集对齐的物理设备槽位向量。

**（3）逐层精确预取**

- 针对跨层共享索引的模型（IndexCache/IndexShare，如GLM-5.2：78层中21个anchor层运行索引器，57个共享层复用前序anchor选择）：
  - anchor层的RESOLVE额外记录其缺失计划（哪些主机记录移入哪些槽位）；
  - 一个copy-only内核在侧流上将该计划重放到各共享层缓存中，与中间层计算重叠；
  - 共享层直接等待预取完成事件并跳过解析，零探测、零同步主机加载、零投机流量浪费。
- 对无共享索引的模型，探索了投机性变体（用第ℓ层选择预测第ℓ+1层），但实测几乎无端到端收益——LRU已捕获大部分隐式跨层复用，而真正的缺失恰恰是提示无法预测的新进入位置。

### 2.4 符号定义

- Lctx：上下文长度；k：每查询选中token数；S_t^(ℓ)：第ℓ层第t步选择集；B：GPU缓存容量（每请求每层槽位数，B≥k）；Nbatch：并发请求数；Nℓ：稀疏注意力层数；WKV：每token每层KV元素数。

## 六、主要结论与发现

1. **显著吞吐提升**：长上下文工作负载下峰值生成吞吐最高提升4.7×（Qwen3+Quest在200K输入，111→520 tok/s）；GLM-5.1+DSA在160K提升2.9×（232→680 tok/s）；DeepSeek-V4-Flash在32K/64并发提升2.1×（600→1257 tok/s）。
2. **增益完全来自批大小效应**：HiSparse并不加快单步解码，而是让相同HBM容纳更大解码批次。解码吞吐与GPU内存容量解耦。
3. **高负载TTFT显著改善**：如DeepSeek-V4-Flash在64并发时平均TTFT从829s降至171s；预填充侧暂存开销几乎为零（低并发下与基线TTFT一致）。
4. **TPOT在重叠范围可比**：在基线尚能服务的并发范围内，HiSparse的TPOT与基线相当（如16并发时15.9 vs 16.0 ms），miss解析开销小于容量收益。
5. **LRU捕获选择局部性**：B=2k时LRU平均miss率13.4%，优于FIFO（17.2%）和随机（16.1%），逼近Bélády最优（8.2%）；B增大到4k时miss率降至6.7%。
6. **精确预取掩盖约一半IO开销**：GLM-5.2上精确预取在匹配并发下降低TPOT 13–15%、提升吞吐14–17%，达到无IO预言机吞吐上限的85%（无预取时为74%）。
7. **解析机制本身零开销**：无IO预言机在低并发下与基线TPOT几乎一致（24.1 vs 24.8ms），证明host-device IO是唯一代价。
8. **快速主机链路改变最优缓存配置**：GH200的NVLink-C2C使IO从112μs降至29μs（GLM-5.1，B=2k，batch=16），B=2k成为更优选择。

- **识别负结果的价值**：明确报告投机性预取无增益，并将结论上升为"共享索引的模型协同设计是正确路径"的设计原则，而非仅仅报告成功案例。

## 八、不足与局限

- **TPOT开销**：在非容量受限场景（短上下文或低并发）下，HiSparse无收益反而承担IO开销（7–8ms/token同步模式下）；论文建议此时直接关闭。
- **主机内存容量约束**：第二层（主机DRAM）的容量是更根本的限制——在Grace-based GB200/GB300上，Grace CPU约480GB LPDDR与GPU聚合HBM相当甚至更小，容量乘数效应大幅缩减；NVMe/网络存储虽可扩展容量但引入更高延迟，更依赖预取有效性。
- **锚层缺失不可避免**：anchor层自身选择无法预先得知，其miss本质上是同步的（GLM-5.2中占21/78层约27% IO）。预取最多隐藏了可作用IO的2/3~4/5。
- **缓存配置为静态参数**：B在部署时固定，未实现动态/准入时调整；论文承认动态策略留给未来工作。
- **与并发系统的对比缺失**：未与ESS、ECHO做直接的端到端基准对比，读者难以评估与最近的同类工作的相对优劣势。
- **PD-disaggregated验证为代理性**：论文声明由于测试平台容量限制，未运行物理分离部署，仅以decode-only曲线作为代理指标。
- **可服务上下文上限的论证依赖理论推导**：对超出HBM容量的超长上下文（如1M token）仅通过内存占用公式论证可行性，未实测验证。
