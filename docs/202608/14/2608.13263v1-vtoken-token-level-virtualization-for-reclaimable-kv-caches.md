## 摘要
大语言模型服务面临一个关键的内存瓶颈：KV缓存随序列长度和批次大小增长。PagedAttention使用固定大小的内存块来减少分配器层面的碎片，但近期的KV驱逐算法以比块级管理更细的分词粒度运行。这种不匹配导致块内碎片，使得大量已分配的KV内存无法回收。我们提出vToken，一种轻量级分词级虚拟化层，将逻辑分词活跃性与物理块放置解耦。vToken通过分词表间接寻址维持稳定的逻辑分词视图，并通过异步重打包活跃分词实现物理回收。该设计保留了PagedAttention内核和CUDA Graph兼容性。我们在vLLM中实现vToken，并使用H2O、Random和Scissorhands在不同模型上进行评估。与配对的Naive-Evict基线相比，vToken使每个请求保留的KV块减少27.2%--72.3%，并在SLA约束下将吞吐量提升最高1.37倍。在受限的活跃KV预算下，它将最大可行并发性提升最高2倍，同时将每种策略的集成工作量从500多行减少到50行以下。

## Abstract
Large language model serving faces a critical memory bottleneck: the KV cache grows with sequence length and batch size. PagedAttention uses fixed-size memory blocks to reduce allocator-level fragmentation, but recent KV eviction algorithms operate at a token granularity finer than block-level management. This mismatch causes intra-block fragmentation, leaving a large fraction of allocated KV memory unreclaimable. We present vToken, a lightweight token-level virtualization layer that decouples logical token liveness from physical block placement. vToken maintains a stable logical token view through token-table indirection and realizes physical reclamation by repacking live tokens asynchronously. The design preserves PagedAttention kernels and CUDA Graph compatibility. We implement vToken in vLLM and evaluate it with H2O, Random, and Scissorhands across models. Compared with a paired Naive-Evict baseline, vToken reduces retained KV blocks per request by 27.2\%--72.3\% and improves SLA-constrained throughput by up to 1.37$\times$. Under a constrained active-KV budget, it extends the maximum feasible concurrency by up to 2$\times$, while reducing the per-policy integration footprint from 500+ lines to under 50.

# vToken：面向可回收KV缓存的分词级虚拟化 —— 论文总结

## 1. 核心问题与整体含义

- **背景：** 大语言模型（LLM）推理服务中，KV Cache 随序列长度和批次大小线性增长，成为 GPU 内存的主要瓶颈。以 13B LLaMA 为例，单 token 约需 0.8 MB KV，32K 上下文时超过 25 GB。
- **现有方案矛盾：**
  - PagedAttention（vLLM）采用固定大小块（默认 16 token/块）管理 KV 内存，减少外部碎片并支持前缀共享，但分配、回收、槽位映射均为块粒度。
  - 近期 token 级驱逐策略（H2O、StreamingLLM、Scissorhands、Random 等）按单 token 判断存活，与块级管理存在**粒度不匹配**。
- **核心问题：** 一个块中同时存在存活和已驱逐 token 时，整个块无法释放，导致大量“块内碎片”（intra-block fragmentation）——逻辑上已可释放的 KV 内存物理上仍被占据。论文初步实验显示，在 16K 上下文下，大量已分配块利用率不超过 50%，块内浪费达 40%-60%。
- **整体含义：** 论文指出，问题的本质是缺少一个“运行时边界”来解耦 token 级存活性与块级物理回收，使 token 级驱逐策略无法在块管理运行时中真正转化为可复用的物理容量。

## 2. 方法论

### 2.1 核心思想
- 引入 **vToken**：一个轻量级 token 级虚拟化层，位于驱逐策略与 PagedAttention 块管理之间。
- **向上**暴露 token 级接口，策略无需理解物理块；
- **向下**维护逻辑到物理映射，通过异步重打包存活 token，回收碎片化的物理块。

### 2.2 关键技术组件
- **Token Table（token 表）：**
  - 每序列维护一张表，记录每个逻辑 token ID 对应的 `(block_id, offset)` 和存活位。
  - 驱逐仅标记逻辑无效，不立即移动物理 KV 数据。
  - 核心接口：
    - `evict_token(req_id, token_id)`：标记逻辑失效；
    - `sync_new_tokens(req_id, block_ids, total_len)`：注册新生成 token；
    - `apply_moves(req_id, moves)`：重定位完成后原子更新映射。
  - 元数据开销小：16K 序列约 256 KB，不足 2GB KV 的 0.1%。

- **物理回收后端（lazy compaction）：**
  1. **回收资格判定**：基于每块存活 token 数 `n_b` 和碎片率 `F`，增量更新，避免全表扫描；
  2. **Headroom-aware 准入**：仅在碎片率超过阈值 `θ_F`（默认 0.25）且保留有界“疏散 headroom”时才触发回收，防止自由块耗尽；
  3. **重定位规划**：请求本地化，选择低利用率源块，计算目标块数 `⌈T_live/S⌉`，仅当投影块数严格减少时才提交计划；
  4. **阶段感知异步拷贝**：将 KV 拷贝放在当前 step 的 forward 之后、post-forward 阶段（采样/调度等）进行，避免与注意力 kernel 争抢 HBM 带宽；通过 CUDA event 保证后续注意力可见拷贝结果。

- **Scheduler 集成：**
  - 修改 slot 映射为 `slot = token_table[token_id].block_id × S + offset`，每次 input 准备时查询一次，不侵入注意力 kernel。
  - 加入三种钩子：headroom 预留、worker 侧回收启动、注意力前同步。
  - 保持 CUDA Graph 兼容：不重新捕获图，仅更新可变槽位映射缓冲，重定位在独立流上运行。

- **正确性不变量：**
  - I1 token 守恒：重定位不改变逻辑 token 身份和 KV 内容；
  - I2 唯一映射：每个活跃 token 唯一对应一个物理槽位，反之亦然；
  - I3 注意力前可见性：重定位复制完成后注意力才能读取；
  - I4 布局感知规划：仅在一致快照上规划，且必须严格减少块数。

- **抽象设计优雅：** 在块管理之上增加一层轻量 token 虚拟化，不修改注意力内核，不破坏 PagedAttention 生态，兼容 CUDA Graph。

- **评估较为全面：** 同时考察内存效率、吞吐、容量边界、开销、灵敏度、前缀缓存、正确性和生成质量，方法论扎实。

## 8. 不足与局限

- **实验范围局限：**
  - 仅单节点、单 GPU；未验证分布式、张量并行或多 KV cache group 场景；
  - 数据集规模有限，主要依赖 ShareGPT/LongBench 和合成前缀，未覆盖超长上下文（>32K）或复杂推理负载。
- **与近期系统的直接比较缺失：** 未将 vToken 与 PagedEviction、Zipage、DiffKV 等做同平台数值对比，定量优势不完全清晰。
- **共享前缀处理保守：** 当前实现跳过共享块，虽有 copy-on-write 扩展设想但未实现验证，可能损失一部分回收潜力。
- **开销仍有优化空间：** planner 端机会检查占主导，异步拷贝虽无显式阻塞，但与解码竞争 GPU 资源，重压下仍可能影响性能。
- **参数敏感性：** 碎片阈值、驱逐比例等需要调优；虽然论文指出阈值不敏感，但默认值的选择仍依赖经验。
- **生成质量评估较浅：** 仅用 ROUGE-L 和输出长度，未评估更丰富的语义质量或下游任务效果；质量变化主要由驱逐策略决定，vToken 本身的“无关性”是间接论证。
- **适用条件受限：** vToken 被设计为“内存压力下的扩展”，当 KV 不是瓶颈时原生路径更优，因此并非所有场景都适用。
