## 摘要
现代 LLM 智能体在持久化工作空间中运行，其累积历史可能同时超出 GPU 的 KV 容量与模型的原生上下文窗口。现有系统通常将较早的上下文压缩为摘要，或稍后以文本形式检索，前者会丢失细粒度的执行证据，后者则需反复预填充模型已经处理过的内容。我们提出 KVMem，一种 KV 上下文虚拟化系统，它将溢出的工作空间历史以分页 KV 状态的形式保存在 GPU 内存、主机内存与 NVMe 之中。KVMem 使用轻量级、模型原生的注意力空间索引来选取相关的历史块，并物化出一个受模型原生上下文窗口约束的、依赖查询的执行视图。在涵盖长达一百万 token 历史的长时间上下文智能体基准（包括 LongMemEval、MemoryAgentBench 和 AgentLongBench）上进行的大量评估表明，与基于压缩的方法（处理上下文溢出的实际标准做法）相比，KVMem 通常能获得更高的任务效用与更高的推理效率。在使用 Qwen3.8-27B 的 DeepSWE 长上下文测试中，KVMem 将任务成功率从仅使用压缩式上下文管理时的 43.8% 提升至 48.4%。在我们的本地部署评估中，KVMem 在一台配备 24 GB RTX 5090 Laptop GPU 的市售笔记本上运行带 MTP 的 Qwen3.6/3.8-27B NVFP4，虚拟化高达 1M token 的智能体工作空间——是模型原生 256K token 上下文窗口的四倍。在单会话设置下，KVMem 的生成速度约为 50 token/s，为本地智能体执行提供了交互式响应能力。更广泛地说，通过将可寻址的工作空间大小与 LLM 的原生上下文窗口解耦，KVMem 为工作空间能够超出该窗口的长期运行智能体提供了一条切实可行的路径。

## Abstract
Modern LLM agents operate in persistent workspaces whose accumulated history can exceed both GPU KV capacity and the model's native context window. Existing systems typically compact older context into summaries or retrieve it later as text, either losing fine-grained execution evidence or repeatedly prefilling content that the model has already processed. We present KVMem, a KV-context virtualization system that preserves overflowed workspace history as paged KV state across GPU memory, host memory, and NVMe. KVMem uses lightweight, model-native attention-space indexes to select relevant historical blocks and materializes a query-dependent execution view bounded by the model's native context window. Extensive evaluations on long-context agent benchmarks spanning histories up to one million tokens, including LongMemEval, MemoryAgentBench, and AgentLongBench, show that KVMem generally achieves higher task utility and greater inference efficiency than compaction-based approaches, the de facto standard for handling context overflow. In the DeepSWE long-context test with Qwen3.8-27B, KVMem improves task success from 43.8% with compaction-only context management to 48.4%.   In our local-deployment evaluation, KVMem runs Qwen3.6/3.8-27B NVFP4 with MTP on an off-the-shelf laptop equipped with a 24\,GB RTX 5090 Laptop GPU, virtualizing agent workspaces of up to 1M tokens-four times the model's native 256K-token context window. In a single-session setting, KVMem generates $\sim$50 tokens/s, providing interactive responsiveness for local agent execution. More broadly, by decoupling addressable workspace size from the LLM's native context window, KVMem provides a practical path toward long-running agents whose workspaces can grow beyond that window.

# KVMem 论文中文总结

## 1. 核心问题与研究动机

- **背景**：现代 LLM 智能体（如 SWE-agent、Codex、Claude Code、OpenHands）运行在持久化工作空间中，会不断累积文件内容、工具输出、日志、编辑记录等历史。这些历史可能同时突破两条边界：
  - **GPU KV 容量**：即使历史仍在模型原生窗口内，模型权重、运行时缓冲、投机解码状态与 KV 缓存也在争夺同一块显存，实际可用上下文远小于标称窗口。
  - **模型原生上下文窗口**：如 Qwen3.6-27B 原生窗口为 256K token，而长上下文智能体基准已包含数十万至数百万 token 的轨迹。
- **现有方案的根本缺陷（文本中心抽象）**：
  - **压缩（Compaction）**：在尚不知道未来哪些细节重要时就做有损摘要，可能丢弃后来变得关键的句子、工具输出值或用户约束。论文用不可区分性论证指出：若 `C(H1)=C(H2)` 但 `H1≠H2`，则仅凭摘要无法恢复被省略的差异。
  - **文本检索（RAG 式）**：虽能找回细节，但检索到的 token 必须重新预填充（prefill），即便这些内容此前已被处理过，导致重复计算。
- **核心洞察**：历史上下文离开活跃窗口时，模型早已把它编码成了 KV 状态，唯一不确定的是"哪一部分会再次被需要"。因此可借鉴虚拟内存思想，**把可寻址 KV 工作空间的大小与 GPU 上物理驻留的 KV 状态解耦**。

## 2. 方法论

### 2.1 核心思想

- 将溢出的工作空间历史保存为**分页 KV 块**，横跨 GPU 显存、主机内存与 NVMe 三层存储。
- 每个智能体步骤只物化一个**有界的、依赖查询的执行视图**（execution view），其大小受限于模型原生窗口与 GPU KV 预算。
- 关键区分三容量：`B_model`（原生窗口）、`B_gpu`（GPU KV 预算）、`B_m`（后备工作空间容量）；有效活跃预算 `B_a = min(B_model, B_gpu)`。

### 2.2 三大机制

**(1) 步骤级内存调度（何时召回）**
- 实证依据：分析 8 条 OpenHands SWE-bench Lite 轨迹的注意力 KL 散度，同一步内相邻窗口平均仅 0.070 bits，跨步骤边界则达 2.59 bits（约 37.3×）。
- 做法：**每个智能体步骤更新一次历史工作集**——在 prefill 之后、decoding 之前执行一次召回，解码期间工作集保持不变，新生成 KV 在尾部增长。

**(2) 查询条件 KV 检索（召回什么）**
- 用 **Mean-K 表示**为每个逻辑块、每层、每个 KV 头构建一个位置无关的紧凑索引：先移除 RoPE 位置编码，再对块内 K 向量取均值：
  - `k̄_{l,b,g} = (1/|b|) Σ_{i∈b} k̃_{l,i,g}`
- 检索时对当前查询做同样的去位置变换，通过缩放点积比较，并在候选块上做全局 softmax 归一化：
  - `R_b = Σ_m mean_{l,h} softmax_{b'∈C}( q_{l,m,h}^T k̄_{l,b',g(h)} / √d )`
- 保留固定的 sink 与 recent 块，其余预算填入得分最高的块，最后恢复时间顺序。
- 默认块大小 **32 token**，索引常驻主机内存，仅分块（tile）流式送入 GPU 打分，使检索显存占用与索引规模无关。

**(3) 分层 KV 管理（如何召回）**
- **仓库视图 vs 执行视图**：仓库视图追踪块在 GPU 页池/主机/NVMe 的有效副本；执行视图只含当前步骤选中块，按时间排序并映射到紧凑位置。通过页表别名（page-table aliasing）避免拷贝到稠密缓存。
- **位置一致的重物化**：保留一份不可变的、位置无关的原始 K（raw K）作为重建权威；对入块在新紧凑位置重新施加 RoPE，V 直接拷贝。已在 GPU 的块可用**有界 delta re-RoPE**，超过阈值后从 raw K 重建以限制数值误差。
- **三项优化**：
  - **主动换出**：在分块 prefill 时异步把已完成块的 KV 复制到主机/NVMe，使换出不再位于恢复关键路径。
  - **检索感知的分层复用**：按工作集差分 `R_t = W_t ∩ W_{t-1}`、`L_t = W_t \ W_{t-1}`、`E_t = W_{t-1} \ W_t`，复用 GPU 命中页；主机内存准入/淘汰同时考虑近期与累积检索频率（优于纯 LRU）。
  - **打包与流水线重物化**：把分散块聚合成连续 pinned 内存缓冲、批量 H2D 传输、GPU 内核 scatter 并 re-RoPE；三级流水（CPU gather / H2D / GPU scatter）以双缓冲与 CUDA event 重叠执行。

### 2.3 系统实现

- 自研 **QW3** 推理引擎（C++/CUDA，面向 Qwen），在单一运行时内控制前向路径、分页 KV 分配器、注意力页表、CUDA 内核与传输流，并支持连续批处理、前缀复用与 MTP 投机解码。
- KVM EM 在其上增加主机端块管理器、检索与 re-RoPE 内核、pinned 内存与 NVMe 后端。

## 6. 主要结论与发现

- **效用**：
  - LongMemEval-S：85.6% 准确率，距 Full Context（86.6%）仅 1.0 个百分点，远高于 Sliding Window（26.8%）与 Compact-only（45.6%）。
  - AgentLongBench ≤256K：60.87% 成功率，**超过** Full Context（59.54%），作者推测是因只暴露查询相关子集可缓解长上下文性能退化。
  - AgentLongBench 1M：50.0%，比 Compact+RAG 高 8 个百分点、比 Compact-only 高 16 个百分点。
  - MemoryAgentBench（>256K）：40.99%，优于 Compact+RAG（34.80%）。
- **效率**：
  - 预答延迟 0.38–1.81 s，相比 Compact+RAG（含压缩）的 26.63–416.38 s，**降低 11.4–53.8×**；即便排除摘要生成时间仍为 10.63–39.24 s。
  - LongMemEval-S 上 KVMem 与 Full Context 一样只处理 109.74K 总输入，但 fresh prefill 仅 0.08K，而 Compact+RAG 需 31.00K fresh prefill。
- **消费级部署**：24 GB 笔记本 GPU 上支持 1M token 虚拟工作空间（原生窗口的 4 倍、GPU 执行视图的 12.5 倍），单会话生成约 50 token/s。
- **可扩展性**：服务器上工作空间从 256K 扩到 10M，GPU 占用几乎恒定（约 34 GiB），增长被主机内存（上限 64 GiB）与 NVMe（8.5→324 GiB）吸收；检索延迟 174 ms→1.311 s，TTFT 0.427→1.601 s，prefill 吞吐约 2K token/s、decode 稳定。
- **长程真实任务**：DeepSWE 上 Pass@1 从 43.8%→48.4%（+4.7 pt），Pass@4 从 81.3%→93.8%（+12.5 pt），16 题中解出 15 题；prefill 时间降低 55.1%（2.23×），agent 时间降低 12.8%，请求墙钟时间降低 15.4%，解码 token 降低 18.7%。

## 7. 优点

- **抽象层面的创新**：把"累积的智能体上下文"识别为可虚拟化的系统资源，明确区分可寻址工作空间、模型可见执行窗口与 GPU 驻留 KV 集，视角清晰且具推广价值。
- **模型原生、非文本的检索信号**：Mean-K 索引直接取自服务模型自身注意力空间，比外部文本检索器更贴合模型真正会关注的状态，且索引极紧凑（10M token 仅 9.5 GiB）。
- **设计有实证支撑**：步骤级调度并非拍脑袋，而是基于 8 条真实轨迹的注意力 KL 分析；块级 top-8 覆盖 66.5%、top-16 覆盖 77.0% 的稀疏性也支撑了块级检索的可行性。
- **系统性工程完整**：从调度、检索、页表别名、raw-K 重建、delta re-RoPE、打包流水线到 NVMe 后台 worker，形成端到端闭环，并自研 QW3 引擎以打通现有服务框架未暴露的接口。
- **实验兼顾受控与真实**：既有可重放的受控基准隔离记忆策略影响，又有 DeepSWE 完整轨迹验证端到端效果；消费级设备实验突出了实用价值。
- **诚实的对比表述**：明确标注哪些对比是严格受控、哪些不是（如公开 DeepSWE 轨迹使用不同 harness）。

## 8. 不足与局限

- **不扩展单次调用的注意力范围**：1M/10M 指可寻址虚拟工作空间，每次模型调用仍受原生窗口与 GPU KV 预算约束，并非让模型一次看更多 token。
- **KV 复用并非数学等价**：历史 KV 原本是在其早期因果上下文中计算的；虽然通过 re-RoPE 与重新 prefill 当前查询保证位置一致，仍与在新上下文下重算不完全相同。
- **检索可能漏块**：每步只物化工作空间的检索子集，任务相关块可能被遗漏；资源允许时更大的执行视图可降低该风险。
- **存储开销显著**：KV 状态远大于文本，10M 工作空间需 324 GiB NVMe；检索延迟随索引增长（10M 时达 1.311 s）。
- **应用限制**：需对 KV 分配、检索、位置恢复与分层搬运有完全控制，**无法透明叠加在黑盒 LLM API 之上**；尚未支持多用户并发服务下的资源竞争。
- **实验覆盖不足**：
  - 缺少对三大机制各自贡献的消融；
  - 块大小（32 vs 更大块）与 Mean-K 近似精度未做敏感性分析；
  - DeepSWE 仅 16 个任务、每任务 4 次采样，统计效力有限；
  - 未报告失败案例分析与检索漏召的具体影响；
  - 消费级实验为单会话设置，未评估并发或长时稳定性。
- **潜在偏差风险**：部分基准（如 AgentLongBench ≤256K）上 KVMem 超过 Full Context，作者以"长上下文退化"解释，但该解释为推测，缺乏直接验证。
