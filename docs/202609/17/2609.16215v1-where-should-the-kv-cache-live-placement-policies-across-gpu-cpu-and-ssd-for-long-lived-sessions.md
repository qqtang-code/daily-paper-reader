## 摘要
GPU 高带宽内存稀缺且昂贵，而随着聊天、智能体循环和文档问答不断累积状态，KV 缓存会消耗其中很大一部分。Mooncake、LMCache、FlexGen、InfiniGen 和 AttentionStore 等系统利用 CPU DRAM 和 SSD 扩展 GPU 内存。更难的问题是：哪些块应属于哪个层级、何时移动或逐出它们，以及预取是否有帮助。我们在一个涵盖 GPU HBM、CPU DRAM 和 SSD 的离散事件模拟器中研究这些选择，并以随机森林执行时间预测器进行校准。我们在聊天、智能体和文档问答工作负载上比较了最近使用、重用频率、预测重用，以及带预取前瞻的 EWMA 预测器。分层存储使每块 GPU 支持的并发会话数提高 73.02 倍，并使每会话成本降至原来的 1/62.04。这些收益来自 1+8+64 的层级容量配置，而非放置策略。在我们的设置中，批大小为 1 时解码是计算受限的，因此放置策略几乎不影响吞吐量。它主要改变 PCIe 迁移流量和首 token 时间。对于聊天负载，最近使用策略产生的迁移流量仅为重用频率策略的 1/2.30。重用频率在智能体和文档问答上表现最佳。现有的预测重用策略与最近使用策略逐字节相同，因此其针对智能体的推荐实际上就是最近使用。真正的 EWMA 预测器会改变行为，但在原本预期预测能有所帮助的工作负载上，其排名仍落后于重用频率。预取无法证明其带宽成本是合理的。在策略与缓存大小的网格上，即使拥有未来请求知识的预言机在迁移流量上也从未胜过不预取。特定于工作负载的放置可以减少数据移动，但按当前实现，预测重用和预取的建议并未得到支持。

## Abstract
GPU high bandwidth memory is scarce and expensive, and KV caches consume much of it as chats, agent loops, and document question answering accumulate state. Systems such as Mooncake, LMCache, FlexGen, InfiniGen, and AttentionStore extend GPU memory with CPU DRAM and SSD. The harder question is which blocks belong in each tier, when to move or evict them, and whether prefetching helps. We study these choices in a discrete event simulator spanning GPU HBM, CPU DRAM, and SSD, calibrated against a random forest execution time predictor. We compare recency, reuse frequency, predicted reuse, and an EWMA predictor with prefetch lookahead across chat, agent, and document question answering workloads. Tiering supports 73.02 times more concurrent sessions per GPU and lowers cost per session by 62.04 times. These gains come from tier capacities of 1 plus 8 plus 64, not placement policy. Decode is compute bound at batch size one in our setup, so placement barely affects throughput. It mainly changes PCIe migration traffic and time to first token. Recency produces 2.30 times less migration traffic than reuse frequency for chat. Reuse frequency performs best for agents and document question answering. The existing predicted reuse policy is byte identical to recency, making its agent recommendation effectively recency. A genuine EWMA predictor changes behavior but still ranks behind reuse frequency on the workloads prediction was expected to help. Prefetching does not justify its bandwidth cost. Across the policy and cache size grid, even an oracle with knowledge of future requests never beats no prefetch on migration traffic. Workload specific placement can reduce data movement, but the predicted reuse and prefetch recommendations are not supported as implemented.

# 论文总结：KV 缓存应该存放在哪里？——跨 GPU、CPU 与 SSD 的放置策略

## 1. 核心问题与研究动机

- **背景痛点**：在 LLM 服务中，GPU HBM 是最稀缺、最昂贵的资源，而 KV cache 是其最大消耗者。长对话、智能体循环、重复文档问答等"长期存活会话"会持续累积 KV 状态，单条长上下文的 KV 已可与模型权重相当，多会话并发时远超 HBM 容量。
- **现有做法**：要么每次恢复会话时从头重算 prefill，要么限制并发数，二者都浪费算力与成本。
- **自然解法**：把 KV block 分层存放到更便宜、更大的 CPU DRAM 与 SSD 中（Mooncake、LMCache、FlexGen、InfiniGen、AttentionStore 等已解决"机制"问题），会话恢复时再取回。
- **真正的开放问题**：**策略**而非机制——哪些块放哪一层？何时提升、降级、驱逐、预取？最优策略如何随工作负载的复用结构变化？层间带宽/延迟差距巨大（HBM 比 SSD 快数百倍），错误放置要么浪费 HBM，要么在解码时因取块而停顿。
- **整体含义**：论文将放置策略本身作为研究对象，机制视为给定，试图给出"按工作负载的放置配方"。

## 2. 方法论

- **核心思想**：构建一个覆盖 GPU HBM → CPU DRAM → SSD 三层的**可配置分层放置层**，用离散事件模拟器研究放置策略空间，并以随机森林执行时间预测器校准。
- **缓存粒度**：采用 PagedAttention 的固定大小 KV block，每个 block 驻留于三层之一；设容量 $c_g \ll c_d \ll c_s$，带宽 $b_g \gg b_d \gg b_s$。
- **算法流程（Algorithm 1，按块访问）**：
  1. 若块已在 HBM，直接使用（命中）；
  2. 否则沿层级向上取块并提升至 HBM；
  3. 若 HBM 满，将得分最低的块降级到 DRAM，必要时级联到 SSD；
  4. 对预测即将使用的块执行预取，提前搬运；
  5. 更新该块的策略得分 $s(b)$，记录命中层级与解码停顿。
- **策略族（对比对象）**：
  - **recency**（LRU 式分层，保留最近使用块在高位）；
  - **reuse frequency**（保留被反复访问的块，利好共享前缀）；
  - **predicted reuse**（论文所称"路线图"的廉价预测器，思路上类似 InfiniGen）；
  - **predictive (EWMA)**：作者自行加入的、基于指数加权移动平均的"真实"下次访问预测器，可证明与 recency 行为不同。
- **预取**：设置 lookahead 窗口，在解码步之前把即将需要的块搬入 HBM，以重叠传输与计算；对 lookahead 深度进行扫描，权衡 HBM 占用与停顿避免。
- **成本模型**：有效容量为 $c_g+c_d+c_s$，混合成本由廉价层主导，因此分层可显著提升每美元可支撑的并发会话数；同时报告实测停顿，避免把内存节省误当成"免费午餐"。

## 3. 实验设计

- **工作负载（按复用结构选取，Table I）**：

  - 预取实验：策略网格 × 缓存大小 × 三种预取臂（无预取、仅用过去访问的因果预测器、读取未来的 oracle），在**竞争带宽计费模型**下进行；

## 6. 主要结论与发现

- **发现一（容量是机制赢，不是策略赢）**：分层把每 GPU 并发会话数提升 **73.02×**、每会话成本降低 **62.04×**，但该倍数恰好等于层级容量倍数 **1+8+64 = 73**，几乎与工作负载复用结构无关；在比例扫描中该比值稳定在 72.68×–73.22×。好的放置策略对这个计数**没有贡献**。
- **发现二（batch=1 下策略主要影响迁移流量与 TTFT）**：解码计算受限，吞吐在各策略间几乎不变（chat 恒为 1307.60 tok/s），因此吞吐是错误的评估视角。策略真正控制的是 **PCIe 迁移流量**：chat 上 recency（=predicted_reuse）为 27.38 GB，reuse-frequency 为 62.99 GB，**recency 少 2.30×**；agent 与 doc QA 上顺序反转，reuse-frequency 分别以 49.36 GB（1.60×）与 48.23 GB（1.63×）胜出。
- **发现三（predicted-reuse 名不副实）**：已发布的 predicted-reuse 策略在每个工作负载上与 recency **逐字节相同**，因此"agent 循环用 predicted-reuse"实际就是 recency，且在 agent 上 recency 还略逊于 reuse-frequency。作者加入的 **EWMA 真实预测器**确实行为不同，但在其本应胜出的工作负载上仍排第二：agent 53.16 GB vs reuse-frequency 49.36 GB，doc QA 48.45 GB vs 48.23 GB（近乎平手），chat 上则大幅落后（57.76 GB）。预测只在**一个狭窄的中间缓存容量窗口**中于 agent 上取得第一。
- **发现四（预取不划算）**：在整个策略 × 缓存大小网格中，因果预测器在**任何单元**都没能捕获 oracle 的正收益份额；而读取未来的 oracle 本身在**超过一半**的单元里比不预取更慢——在竞争链路上，投机取块会推迟正在等待的需求取块，代价超过其消除的停顿。
- **延迟去向**：每 token 解码中计算占主导（约 13.2445 ms/token），取块停顿在**所有工作负载上都低于 TPOT 的 1%**，说明分层取块被计算掩盖；也说明 TPOT 不是区分策略的好指标，真正的差异在 TTFT 与迁移带宽。
- **命中率分布**：DRAM 是主力层（chat 61.87%、agent 72.65%、doc QA 68.48%），SSD 只是浅层后备（doc QA 8.80%、agent 6.07%），残余需重算的 miss 约 13.62%–14.15%。
- **成本-延迟前沿（E11）**：成本是组成的纯函数，跨 8.38×（$45,493–$381,287 每 1k 会话）；而 P99 TTFT 在整个扫描中最多只移动其上限的 **10.1%**（多组不足 1%），前沿近乎垂直，**倾向廉价、SSD 重的组成**；最便宜组成 HBM/DRAM/SSD = 10/86/96 在全部 12 组中都是最便宜点，且延迟代价几乎免费。
- **容量-SLO（E10）**：加深 SSD 可将会话数最大化 **10.77×**（容量驱动、各工作负载一致），但延迟代价不免费：chat 与 agent 在整个 SSD 深度范围内**从未满足** SLO；只有 doc QA 在深度 64 处首次满足，且在最深处仅以 **0.000 ms 余量**恰好压线，同时仍支付 4.42 ms 平均停顿。
- **总体配方**：分层是机制赢，策略是带宽-延迟的二阶决策；可用配方是 **并发 chat 用 recency**（单条孤立长对话下所有策略相同，廉价 LRU 天然正确，容量是唯一杠杆）、**重复 doc QA 用 reuse-frequency**；"predicted-reuse" 与"+ prefetch" 两部分按当前实现不成立。

## 7. 优点

- **诚实报告负面结果**：明确报告 predicted-reuse 与 recency 逐字节相同、EWMA 预测器仍败北、预取在竞争链路上不划算，这类"不成立"的结论对社区同样有价值。
- **方法学严谨**：对关键论断做代码级验证（策略等价性、成本函数的纯组成依赖），并在协议中**主动披露** chat 用 6 并发而非单会话的原因，避免结果被误读。
- **评估视角正确**：指出 batch=1 下吞吐是错误指标，转而聚焦放置真正控制的 PCIe 迁移流量与 TTFT，方法论上有澄清价值。
- **上界式压力测试**：预取实验中引入"读未来 oracle"作为不可能实现的上界，仍无法胜出，使否定结论更硬。
- **多维度系统扫描**：策略、粒度、预取 lookahead、层级比例、缓存大小、层级组成多维覆盖，并给出成本-延迟前沿与 SLO 切片两个部署视角。
- **分离关注点清晰**：把"容量/成本收益（机制）"与"带宽/延迟决策（策略）"明确解耦，避免把容量红利误记为策略功劳。

## 8. 不足与局限

- **合成轨迹偏差**：策略对比基于构造性合成生成器，复用结构天然利于匹配策略，真实对话轨迹复用更低、策略差距会压缩，因此报告的策略分离度是**上界**。
- **batch=1、单 GPU 限制**：此设置下 decode 计算受限、停顿 < 1% TPOT，会**系统性低估**放置与预取在大 batch、更快解码内核下的价值；作者也承认届时停顿份额与预取价值会上升。
- **成本与容量数字依赖假设**：会话数/成本来自固定层价下的容量模型，精确但代表性仅取决于价格假设；$/GB 是默认参数而非市场报价。
- **停顿归因近似**：DRAM/SSD 对解码停顿的贡献是按命中份额**近似归属**，模拟器并未记录某个停顿毫秒来自哪一层。
- **未与压缩/驱逐协同**：KV 量化与驱逐会先缩小块再放置，本文将其固定以隔离放置变量，因此未覆盖放置与压缩的组合效应。
- **预取模型单一**：预取结论建立在"投机取块与需求流量竞争同一链路"的计费模型上，作者也指出在拥有充裕空闲带宽的系统中预取仍然有益，故结论不能外推到所有场景。
- **应用限制**：结论面向长会话服务（chat/agent/doc QA）的模拟场景，真实部署需结合具体带宽、价格、batch 与硬件配置重新校准。
